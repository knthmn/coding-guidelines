# User Experience

Applies when: Any project with a user interface.

Read a rule file only when the rule may apply. The file of rule `<rule-id>` is `rules/<rule-id>.md`.

- `announce-async-updates` [medium] Use `role="status"` or `aria-live="polite"` for routine updates and inline validation. Use `role="alert"` only for urgent errors. Never show critical information only in a toast. When: Code shows toasts, saved or loading messages, counters, or inline validation that appear without a page change.
- `button-labels-name-the-action` [low] Start button labels with a verb that says what happens, such as "Delete project". Avoid OK, Yes and No. Use one label for the next step in a flow, for example Continue. When: Code adds buttons, confirmation dialogs or multi-step flows with text labels.
- `confirm-destructive-actions` [medium] Ask for confirmation before an action that deletes data or cannot be reversed, in a dialog that names the action, or provide Undo for a safe window. When: A button or menu item deletes, removes, revokes or overwrites data, or sends something that cannot be recalled.
- `connect-errors-to-fields` [medium] Place the error next to its field, set `aria-invalid` on the field and link the message with `aria-describedby`, so assistive technology reads it with the field. When: A form field shows an error message or helper text.
- `consistent-ui-wording` [low] Use sentence case, address the reader as "you", name each thing the same way everywhere, describe where links go, and word toggles by what they do when on. When: Code adds or changes visible interface text, such as labels, headings, buttons, links, toggles or messages.
- `date-input-fields` [low] For a date the user knows, such as birth date, use grouped day, month and year fields with a legend, accept month names, set `autocomplete="bday"`, and never auto-advance focus. When: A form asks for a date the user already knows or can look up without a calendar.
- `dont-rely-on-color-alone` [medium] Pair every color-coded state, such as error, success or selected, with text, an icon or another visible cue. When: Code styles status, validation, selection or severity by color.
- `dont-truncate-or-block-input` [medium] Do not drop keystrokes with key filters or `maxlength`. Accept the input and show validation feedback, and ask for a limit in the hint. When: A text field restricts which characters or how many characters it accepts, using `keydown` filters, `onChange` rewrites or `maxlength`.
- `dont-use-field-errors-for-service-problems` [low] Use field validation errors only for input the user can fix. For ineligible users, missing permission or service failures, show a page or banner that explains the cause and the next step. When: Code shows an error next to a field or in a summary for an outcome that is not about the entered value.
- `empty-states-offer-action` [low] When a list or view has no content, say what belongs there and offer one clear action. Do not render a blank area or "No results". When: A list, table, search or dashboard can render with zero items.
- `error-message-names-the-field` [low] Use a different message for each failure state, name the field in the message, and use the same text in the summary and next to the field. When: Code defines validation messages, or shows the same error in more than one place.
- `error-message-wording` [low] Error messages describe the problem and the fix in plain, neutral words. No blame, no codes, no please, sorry, oops, valid or invalid. When: Code adds or changes the text of validation errors, failure toasts or error states.
- `focus-first-error-on-submit` [medium] After a failed submit, move focus to an error summary or to the first invalid field. If you show a summary, title it, and link each entry to its field. When: A form validates on submit and can show errors.
- `format-for-locale` [medium] Format dates, times, numbers and currency with `Intl` or the framework's formatter and the user's locale, not hand-built strings. Pick the language from browser preferences, not IP. When: Code renders dates, times, numbers, currency or units, or picks the interface language.
- `gestures-have-alternatives` [medium] Offer a tap, click and keyboard path for any drag, swipe, pinch or path-based action, unless the gesture is the essential part. When: Code handles drag, swipe, pinch, drag-to-reorder, sliders or range controls.
- `keep-browser-zoom-enabled` [medium] Never disable zoom with `maximum-scale` or `user-scalable`. Set input font size to 16px or more on mobile to stop iOS Safari from zooming on focus. When: The project sets a viewport meta tag or styles the font size of inputs, selects or textareas.
- `keep-input-on-error` [medium] After a failed submit, show the form again with every value the user entered, valid and invalid. Do not clear or reset fields. When: A form submit can fail validation on the client or the server.
- `keep-submit-enabled` [medium] Do not disable a submit button because the form is empty or invalid. Let the user submit, then show what is wrong. Disable only while the request runs. When: A form has a submit button whose disabled state depends on field values or validity.
- `limit-text-with-character-count` [low] For a textarea with a length limit, show the remaining count, let users type past the limit, and report the overflow with a specific error. Use a count only when a limit is needed. When: A textarea or long text field has a maximum length.
- `minimum-hit-target-size` [low] Give controls a clickable area of at least 24 by 24 px, and 44 px on touch screens. Expand the hit area with padding or a pseudo-element when the visible icon is smaller. When: Code styles icon buttons, checkboxes, radios, close buttons, tags or inline controls.
- `navigation-uses-real-links` [medium] Navigate with an `<a>` that has an `href`, or the router's link component. Do not use a button or div with a click handler that sets the location. When: A click handler calls `router.push`, `navigate`, `window.location` or similar to go to another page.
- `never-block-paste` [medium] Do not prevent paste in inputs or textareas, including password, confirm-email and one-time-code fields. When: An input or textarea handles `onPaste`, or sets attributes or listeners that stop paste.
- `normalize-input-before-validating` [medium] Trim whitespace, strip spaces and separators, and accept common formats before validating, so users do not see errors for input that is clear. When: Code validates free-text input such as codes, phone numbers, postcodes, card numbers, emails, names or dates.
- `page-title-reflects-state` [medium] Set a unique document title for each page or view. When a page shows validation errors, add an `Error:` prefix so screen readers announce it first. When: Code sets `document.title` or a title in route metadata, or a page can show validation errors.
- `persist-view-state-in-url` [low] Store filters, search, sort, tabs, pagination and open panels in the URL, so refresh, Back, Forward and shared links restore the view. When: A page keeps filters, tabs, pagination, sort or similar view state in component state.
- `placeholder-not-label` [medium] Give every field a visible label. Use a placeholder only for an extra example, never for the field name, the instructions or the format. When: An input or textarea has a placeholder, or has no visible label.
- `prevent-double-submit` [high] Block repeat submits while a request is in flight, keep the button label, show progress, and protect the server too, for example with an idempotency key. When: A button or form triggers a request that creates, sends, charges or deletes something.
- `set-autocomplete-and-spellcheck` [medium] Add `autocomplete` tokens and meaningful names to personal data fields. Set `spellcheck="false"` for emails, codes and usernames. Avoid names that trigger password managers on other fields. When: A form asks for personal data, credentials, one-time codes, usernames or identifiers.
- `set-input-type-and-inputmode` [medium] Use `type` and `inputmode` that match the value, for example `type="email"`, `type="tel"` and `inputmode="numeric"`. Do not use `type="number"` for IDs, codes, phone numbers or other digit strings. When: A form has text inputs for emails, numbers, phone numbers, codes, URLs or search.
- `validate-on-submit-not-blur` [medium] Show validation errors after the user submits or moves to the next step. Do not show an error on blur or on each keystroke, unless the feedback prevents wasted effort. When: Code validates form fields on change or blur and shows errors.
- `warn-on-unsaved-changes` [medium] When leaving a page or closing an editor would discard edits, warn first or save a draft. When: A form, editor or dialog holds user edits that are not yet saved, and the user can navigate or close it.
